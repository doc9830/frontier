# FRONTIER — первый игровой прототип

Ты разрабатываешь первый playable prototype игры **FRONTIER**.

Это не обычная космическая RPG и не клон существующей игры.

Главная идея:

> Игрок не проходит заранее написанную историю. Он живёт в процедурно созданной космической вселенной, которая сама развивается.

Игрок может исследовать, торговать, добывать ресурсы, покупать и улучшать корабли, создавать собственную космическую станцию и небольшой флот.

Главный приоритет первого прототипа:

**игра должна быть уже приятной и залипательной, даже если в ней пока мало контента.**

Не делай архитектуру для MMO и не создавай сложные системы, которые пока не нужны.

---

# 1. ТЕХНОЛОГИЯ

Сделай игру как PWA / web application.

Предпочтительно:

* TypeScript
* React
* Vite
* CSS
* Canvas или SVG для карты
* IndexedDB или простое локальное хранилище для save

Игра должна запускаться локально:

```bash
npm install
npm run dev
```

Не использовать backend в первом прототипе.

Не использовать регистрацию.

Не использовать multiplayer.

Не использовать внешнюю БД.

Сохранение должно работать локально в браузере.

---

# 2. ОСНОВНАЯ ИДЕЯ ПРОТОТИПА

Игрок начинает с:

* 10 000 credits
* одного небольшого корабля Scout
* маленькой базовой станции
* одного исследованного космического сектора

Вселенная генерируется из seed.

Например:

```text
SEED: FRONTIER-001
```

Один и тот же seed должен генерировать одинаковую вселенную.

---

# 3. ПРОЦЕДУРНАЯ ВСЕЛЕННАЯ

Создай небольшую вселенную для прототипа:

* 20–30 звёздных систем
* 3–4 фракции
* 5–8 типов ресурсов
* несколько торговых маршрутов
* несколько астероидных поясов
* несколько станций
* несколько планет

Каждая система должна иметь:

```ts
System {
    id
    name
    position
    faction
    population
    security
    resources
    stations
    connections
}
```

Не нужно создавать реалистичную астрофизику.

Это игровая процедурная карта.

---

# 4. ФРАКЦИИ

Создай 3–4 фракции.

Например:

```text
Federation
Helix Corporation
Free Colonies
Border Union
```

Фракции должны иметь:

* название
* цвет
* отношение к игроку
* экономические предпочтения
* контроль над системами

Пока не делай сложную дипломатию.

Достаточно репутации:

```text
-100 ... +100
```

Репутация должна влиять хотя бы на:

* цены
* доступность некоторых контрактов
* безопасность территории

---

# 5. РЕСУРСЫ

В прототипе достаточно:

```text
Food
Fuel
Metal
Electronics
Medicine
Rare Ore
Artifacts
```

Не добавляй десятки ресурсов.

Каждая система должна производить одни ресурсы и потреблять другие.

Например:

```text
K-184

Metal

Food
Electronics
```

Цены должны немного зависеть от локального спроса и предложения.

# 7. УЛУЧШЕНИЯ КОРАБЛЕЙ

Добавь простую систему модулей.

Модули:

```text
Engine
Jump Drive
Shield Generator
Reactor
Cargo Module
Scanner
Weapon System
```

Модули должны иметь уровни.

Например:

```text
Engine Mk I
Engine Mk II
Engine Mk III
```

Но улучшения должны иметь компромиссы.

Пример:

```text
Engine Mk II
+20% speed
+5 power consumption
```

```text
Cargo Module Mk II
+25 cargo
-5% speed
```

Не превращай это в RPG с сотнями параметров.

---

# 8. ЭНЕРГИЯ КОРАБЛЯ

Добавь простой power budget.

Например:

```text
Reactor: 100 power

Engine: 20
Shield: 25
Scanner: 10
Weapons: 25
Cargo systems: 10
```

Если игрок устанавливает слишком много мощных модулей, ему нужен более мощный reactor.

Это должно создавать интересные решения при сборке корабля.

---

# 9. ПЕРЕМЕЩЕНИЕ

Не делай ручное управление кораблём.

Игрок выбирает систему на карте:

```text
[ JUMP ]
```

После этого начинается перелёт.

Показывай:

```text
TRAVEL TO K-092

Distance: 6 jumps
Estimated time: 38 sec
Fuel: -12
Risk: LOW

[ JUMP ]
```

Во время перелёта может произойти событие.

Но события должны быть редкими.

Не надо постоянно атаковать игрока.

---

# 10. СОБЫТИЯ

Типы:

```text
Nothing happened
Distress signal
Abandoned cargo
Pirate encounter
Rare signal
Trade opportunity
Unknown anomaly
Derelict ship
```

Вероятности должны быть низкими.

Большая часть перелётов должна быть спокойной.

Цель:

**игрок не должен чувствовать, что игра постоянно его дёргает.**

---

# 11. ПРОСТОЙ БОЙ

Не делай realtime combat.

При встрече с пиратом:

```text
PIRATE INTERCEPTOR

Threat: MEDIUM

[ FIGHT ]
[ ESCAPE ]
[ GIVE CARGO ]
[ EMERGENCY JUMP ]
```

При выборе FIGHT результат определяется характеристиками:

* combat
* shield
* hull
* speed

Можно сделать несколько раундов расчёта.

Игрок должен понимать:

> «Я могу победить, но могу и потерять корабль».

Не нужно делать полноценную боевую игру.

---

# 12. СТАНЦИЯ ИГРОКА

Это важнейшая новая система.

Игрок начинает с небольшой станции.

Название:

```text
FRONTIER STATION
```

У станции есть главное здание:

```text
Command Center
```

Уровни 1–10.

Повышение Command Center:

* открывает новые здания
* увеличивает storage
* увеличивает лимит флота
* увеличивает количество производственных слотов

---

# 13. ЗДАНИЯ СТАНЦИИ

В первом прототипе достаточно:

### Command Center

Главное здание.

### Warehouse

Хранение ресурсов.

### Dock

Приём и обслуживание кораблей.

### Mining Hub

Позволяет отправлять корабли на добычу.

### Refinery

Перерабатывает:

```text
Ore -> Metal
Gas -> Fuel
```

### Shipyard

Ремонт и улучшение кораблей.

### Radar

Увеличивает обнаружение объектов.

### Research Lab

Небольшая система исследований.

### Fleet Office

Управление собственным флотом.

Не добавляй больше зданий без необходимости.

---

# 14. СТРОИТЕЛЬСТВО

Строительство должно быть похоже на старые браузерные стратегии, но значительно проще.

У каждого здания:

```text
level
cost
buildTime
requirements
```

Например:

```text
Warehouse II

Cost:
Metal 500
Electronics 100
Credits 1500

Build time:
45 sec
```

После запуска строительство продолжается независимо от того, находится игрок на другом экране или нет.

После перезагрузки браузера состояние должно восстановиться.

Не надо делать realtime simulation каждую миллисекунду.

Храни:

```text
startedAt
finishAt
```

и вычисляй состояние при загрузке.

---

# 15. СЛОТЫ СТАНЦИИ

Не делай свободную строительную игру.

Станция состоит из ограниченного количества слотов.

Например:

```text
Command Center
      ↓
8 building slots
```

Command Center II:

```text
10 slots
```

Command Center III:

```text
12 slots
```

Это ограничивает сложность.

Игрок должен выбирать:

> Мне сейчас нужен ещё один склад или refinery?

# 24. ВИЗУАЛЬНЫЙ СТИЛЬ

Это очень важно.

Не делать современный яркий мобильный sci-fi интерфейс.

Нужен стиль:

**retro-futuristic computer terminal + modern UX.**

Визуальные ориентиры:

* CRT
* старые космические компьютеры
* минималистичный sci-fi
* монохромная/ограниченная палитра
* тонкие линии
* техническая типографика
* небольшое свечение
* простые пиктограммы
* grid
* координаты
* технические обозначения

Но UX должен быть современным:

* понятные кнопки
* контекстные панели
* dropdown/context menus
* понятные статусы
* hover states
* tooltips
* нормальная адаптация под телефон
* крупные touch targets на мобильном

НЕ делать:

* огромные панели
* декоративные рамки вокруг всего
* нечитаемый пиксельный шрифт
* постоянную анимацию
* перегруженный HUD
* 3D
* реалистичный космический фон с миллионом деталей

Главное:

**ретро должен быть визуальным языком, а не препятствием для управления.**

# 26. ПЕРВЫЙ PLAYABLE LOOP

После запуска игрок должен иметь возможность:

1. увидеть карту;
2. выбрать систему;
3. совершить jump;
4. получить случайное небольшое событие;
5. заработать credits;
6. купить ресурс;
7. продать ресурс;
8. обнаружить астероид;
9. отправить Miner;
10. дождаться возвращения;

12. построить Warehouse;
13. улучшить корабль;

Если эти 15 действий работают приятно — первый прототип считается успешным.

# 30. SIMULATION

Не симулируй мир каждую миллисекунду.

Используй timestamp-based simulation.

Например:

```ts
lastSimulationTime
```

При загрузке:

```text
elapsed = currentTime - lastSimulationTime
```

и пересчитай:

* добычу;
* производство;
* строительство;
* полёты;
* рынок;
* события.

Это позволит игре работать даже если игрок закрыл вкладку.

# 35. ВАЖНО

Не пытайся сделать FRONTIER полноценной игрой сразу.

Первый результат должен быть **маленькой, но реально играемой песочницей**.

Если приходится выбирать между:

```text
20 систем + 50 механик
```

и

```text
8 систем + 10 механик, которые действительно приятно работают
```

выбирай второй вариант.

Главный приоритет:

**GAMEPLAY > CONTENT > ARCHITECTURE > VISUAL POLISH**

Но визуальный стиль должен быть заложен с самого начала, чтобы прототип уже ощущался как FRONTIER.
